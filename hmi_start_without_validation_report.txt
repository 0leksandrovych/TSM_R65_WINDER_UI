HMI START WITHOUT VALIDATION REPORT
===================================

1. Фактична причина блокування START
------------------------------------

У старому UI flow були два послідовні validation gates:

1) На setup screen кнопка START перевіряла одночасно
   hmi_job_draft_model_get_validation()->valid і state->job_state ==
   HMI_JOB_VALID. Якщо умова не виконувалася, callback не відкривав confirmation,
   а викликав hmi_actions_validate_job(), встановлював
   HMI_PENDING_VALIDATE_JOB і надсилав HMI_CMD_VALIDATE_JOB.

2) На confirmation screen can_start() повторно вимагав
   state->job_state == HMI_JOB_VALID та validation->valid.

Controller client мав command binding
HMI_CMD_VALIDATE_JOB -> HMI_CONTROLLER_MSG_VALIDATE_JOB, але UART codec для
HMI_CONTROLLER_MSG_VALIDATE_JOB повертає false як unsupported. Отже production
UART path не міг завершити обов'язкову validation-послідовність, а без result
START залишався недоступним.

Символ hmi_controller_client_validate_job() у фактичному коді відсутній.
Реальний validation path реалізований через hmi_actions_validate_job(),
command bus, binding у hmi_controller_client.c та transport send.

2. Старий flow
--------------

Edit parameters
-> setup START/VALIDATE callback
-> якщо немає validation success: HMI_CMD_VALIDATE_JOB
-> HMI_PENDING_VALIDATE_JOB
-> HMI_CONTROLLER_MSG_VALIDATE_JOB
-> mock response або unsupported UART codec path
-> validation result
-> HMI_JOB_VALID + validation->valid
-> confirmation screen
-> START enabled
-> HMI_CMD_START_JOB.

На UART відсутність завершеного VALIDATE_JOB блокувала перехід/START.

3. Новий flow
-------------

Edit parameters
-> setup REVIEW
-> hmi_actions_open_confirm_start()
-> confirmation показує актуальні draft values
-> START WINDING доступний при machine state READY та safety_ok
-> click перевіряє, що HMI_PENDING_START_JOB не активний
-> hmi_actions_confirm_start_job()
-> HMI_PENDING_START_JOB
-> HMI_CMD_START_JOB
-> hmi_controller_client command binding
-> HMI_CONTROLLER_MSG_START_JOB + current job payload
-> existing UART або mock transport
-> очікування command accepted/rejected і controller telemetry.

UI не змінює machine/job state локально після START click. Action лише
встановлює START pending, refresh-ить navigation і emit-ить HMI_CMD_START_JOB.
Наявний coordinator очищає pending на accepted/rejected/timeout; authoritative
machine state надходить від controller/mock state update.

4. Виконані зміни
-----------------

- components/winder_hmi/src/screens/screen_conical_setup.c
  Видалено активну VALIDATE-кнопку та validation gate. REVIEW безумовно відкриває
  confirmation. Job row тепер описує configured draft, а informational label не
  пропонує недоступну Validate-дію.
- components/winder_hmi/src/screens/screen_confirm_start.c
  Видалено validation readiness row та залежність START від job_state/
  validation result. START залежить від READY, safety_ok і відсутності власного
  HMI_PENDING_START_JOB. Значення параметрів і далі читаються з draft та
  formatter-яться через descriptors.
- components/winder_hmi/src/controller/hmi_mock_controller.c
  MOCK_OP_START_JOB тепер descriptor-driven валідовує отриманий START_JOB
  payload без вимоги попереднього MOCK_OP_VALIDATE_JOB. Accepted/rejected і
  mock state update залишаються controller-side.
- hmi_start_without_validation_report.txt
  Створено цей звіт.

Job schema, scales, START_JOB payload/frame, message IDs, UART architecture,
telemetry, command adapter, generated artifacts і codec architecture не
змінювалися цим інкрементом.

5. Validation subsystem, що залишилася
--------------------------------------

Subsystem навмисно не видалено:

- HMI_CMD_VALIDATE_JOB та HMI_CONTROLLER_MSG_VALIDATE_JOB enums залишилися.
- HMI_PENDING_VALIDATE_JOB, timeout mapping і coordinator handling залишилися.
- hmi_actions_validate_job() та client command binding залишилися, але UI screen
  більше не має caller-а цієї action.
- validation result event/API, coordinator apply path і draft validation
  structures залишилися для майбутнього використання.
- mock explicit VALIDATE_JOB operation залишилася сумісною зі старим API.
- codec case HMI_CONTROLLER_MSG_VALIDATE_JOB залишився unsupported/dormant.
- local descriptor-based validation у hmi_job_draft_model_set_value() та
  hmi_param_validate_value() збережена.
- home-screen informational HMI_JOB_VALID display/shortcut може і далі
  відображати controller state, але setup -> confirmation -> START flow від
  цього стану не залежить.

Ці елементи більше не блокують production START, бо жоден setup/confirmation
screen не викликає hmi_actions_validate_job(), validation pending не входить до
умов navigation/START, а єдиний pending gate на confirmation — START_JOB pending.

6. Mock та UART consistency
----------------------------

Обидва transport-и отримують однаковий HMI flow і однаковий wire-ready
HMI_CONTROLLER_MSG_START_JOB payload. UART передає його через наявний codec та
hmi_uart_transport. Mock ставить MOCK_OP_START_JOB і валідовує payload усередині
controller-side handler перед accepted/rejected; окрема UI VALIDATE_JOB команда
для цього не потрібна.
